# 2. PRÉSENTATION DU PROJET

EduNote est une application mobile destinée aux enseignants qui interviennent dans une ou plusieurs écoles et souhaitent gérer facilement les notes de leurs élèves.

Dans de nombreux établissements scolaires, les enseignants utilisent encore des cahiers, des feuilles de calcul ou des documents papier pour enregistrer les interrogations, les devoirs et calculer les moyennes.

Cette méthode présente plusieurs difficultés :

- Risque de perte des informations.
- Erreurs dans les calculs.
- Difficulté à gérer plusieurs classes.
- Difficulté à retrouver les notes d'un élève.
- Temps important consacré aux calculs manuels.
- Difficulté à préparer les relevés de notes.

EduNote doit résoudre ces problèmes en centralisant toutes les informations dans une application mobile.

L'enseignant pourra gérer plusieurs établissements, plusieurs classes, plusieurs matières et plusieurs élèves.

Il pourra saisir les notes des interrogations et des devoirs, consulter les moyennes calculées automatiquement et exporter les résultats.

L'application doit être adaptée au contexte scolaire africain, particulièrement béninois, tout en restant suffisamment flexible pour d'autres systèmes éducatifs.

# 3. PHILOSOPHIE DE L'APPLICATION

EduNote repose sur cinq principes fondamentaux.

## 3.1. Simplicité

L'application doit être compréhensible par un enseignant qui ne possède aucune compétence technique.

Les principales opérations doivent être faciles à effectuer.

## 3.2. Autonomie

L'application doit fonctionner intégralement sans connexion Internet.

Aucun serveur distant ne doit être nécessaire.

## 3.3. Confidentialité

Toutes les données enregistrées appartiennent exclusivement à l'enseignant.

Aucun administrateur, établissement scolaire ou autre utilisateur ne doit pouvoir y accéder à distance.

## 3.4. Contrôle des données

L'enseignant peut :

- Consulter ses informations.
- Modifier ses informations.
- Exporter ses données.
- Sauvegarder ses données.
- Restaurer ses données.
- Supprimer certaines informations.
- Effacer toutes ses données.

## 3.5. Fiabilité

Les calculs des notes doivent être exacts, cohérents et testés.

Les opérations de sauvegarde doivent préserver l'intégrité des données.

# 15. RÈGLES DE CALCUL DES MOYENNES

CETTE SECTION EST PRIORITAIRE.

Le système de calcul doit respecter exactement les règles suivantes.

## 15.1. Moyenne des interrogations

Une matière peut contenir plusieurs interrogations.

Exemple :

Interrogation 1 : 12/20.

Interrogation 2 : 16/20.

Interrogation 3 : 14/20.

La moyenne des interrogations est :

MI = (12 + 16 + 14) / 3

Résultat :

MI = 14/20.

Cette moyenne doit être affichée distinctement.

## 15.2. Moyenne de la matière

La moyenne finale d'une matière est calculée à partir de trois éléments :

1. La moyenne des interrogations.
2. La note du devoir 1.
3. La note du devoir 2.

Formule :

**Moyenne matière = (Moyenne interrogations + Devoir 1 + Devoir 2) / 3**

Exemple :

Moyenne interrogations : 14.

Devoir 1 : 13.

Devoir 2 : 16.

Moyenne matière :

(14 + 13 + 16) / 3 = 14,33/20.

## 15.3. Actualisation automatique

Chaque fois qu'une note est :

- Ajoutée.
- Modifiée.
- Supprimée.

Les résultats concernés doivent être recalculés.

L'interface doit afficher les nouvelles moyennes immédiatement après la validation locale de l'opération.

## 15.4. Notes manquantes

Ne jamais remplacer automatiquement une note manquante par zéro.

Si le devoir 1 ou le devoir 2 n'a pas encore été renseigné, la moyenne finale de la matière doit être considérée comme incomplète.

Afficher par exemple :

« Moyenne en attente ».

La moyenne des interrogations doit néanmoins rester visible.

## 15.5. Absences

Prévoir plusieurs états :

- Note renseignée.
- Note non renseignée.
- Élève absent.

Une absence ne doit pas automatiquement valoir zéro.

Prévoir une distinction entre une absence et un zéro réellement attribué.

## 15.6. Barèmes

Utiliser /20 comme barème de référence pour les moyennes.

Si une évaluation utilise un autre barème, normaliser la note sur 20 avant son intégration au calcul.

Exemple :

8/10 = 16/20.

## 15.7. Arrondis

Afficher les moyennes avec deux chiffres après la virgule.

Effectuer les calculs avec une précision suffisante.

Ne pas arrondir inutilement les résultats intermédiaires.

## 15.8. Tests

Créer des tests unitaires couvrant :

- Une interrogation.
- Plusieurs interrogations.
- Deux devoirs renseignés.
- Un devoir manquant.
- Aucune interrogation.
- Une note égale à zéro.
- Une absence.
- Une modification de note.
- Une suppression de note.
- Des barèmes différents.
- Des moyennes décimales.

Centraliser toute cette logique dans la couche Domain.

Aucun calcul métier complexe ne doit être directement écrit dans les widgets.

Permettre de sélectionner un fichier de sauvegarde.

Avant la restauration :

- Vérifier le format.
- Vérifier la version.
- Vérifier l'intégrité.
- Déchiffrer le fichier.
- Vérifier la compatibilité.

Afficher une confirmation avant de remplacer les données existantes.

La restauration doit être atomique ou disposer d'un mécanisme fiable de retour arrière.

Une restauration échouée ne doit pas détruire les données existantes.

## 19.3. Suppression complète

Dans les paramètres, proposer :

« Supprimer toutes mes données ».

Afficher un avertissement explicite.

Après confirmation et vérification locale appropriée, effacer :

- Les établissements.
- Les classes.
- Les élèves.
- Les évaluations.
- Les notes.
- Les données de profil.
- Les autres données applicatives locales.

Ne pas affirmer que cette action supprime automatiquement des sauvegardes déjà exportées dans des emplacements externes.

# 23. GESTION DES ÉTATS AVEC SETSTATE

Toutes les pages nécessitant des interactions doivent utiliser StatefulWidget lorsque cela est pertinent.

Les états classiques doivent être gérés avec setState() :

- isLoading.
- isSaving.
- errorMessage.
- selectedSchool.
- selectedClass.
- selectedSubject.
- selectedPeriod.
- Données chargées.

Exemple de fonctionnement attendu :

1. L'utilisateur ouvre une page.
2. La page appelle un Use Case.
3. L'état de chargement est activé.
4. Le Use Case récupère les données via le Repository.
5. La page reçoit les résultats.
6. setState() actualise l'interface.
7. L'état de chargement est désactivé.

Prévoir les vérifications de cycle de vie nécessaires avant l'appel à setState() après une opération asynchrone.

Ne pas mélanger la logique métier avec la logique de présentation.

Ne pas créer de système complexe de gestion d'état qui contourne la préférence pour setState().
